# Mechanism re-check on the GB10 0.23.0 profile

**Post-hoc.** The analysis is on main `70de487`, with the core built clean from it (`result_class` formal). It compares `profiles/gb10.json` (`0.22.0-posthoc`, SHA-256 `10625fa4...`) with `profiles/gb10-0.23.0.json` (`0.23.0`, SHA-256 `f5fa8ecc...`).

It only reads: no core, profile or rule changes, and no sealed label is touched. It is CPU only.

The tool is `scripts/recheck_mechanisms.py` ([baseline](v0.3-mechanism-recheck-baseline.md)). The full output is in [v0.3-gb10-0230-mechanism-recheck.json](v0.3-gb10-0230-mechanism-recheck.json).

The 0.22.0 microbenchmarks are short launches, and the 0.23.0 values are medians of five long-launch processes, so the old column serves for comparison only.

## 1. Per mechanism

Noise here is the median, over a mechanism's points, of the span of the five round medians over the value in the 0.23.0 profile. It is the measured side's repeatability. The 0.22.0 values carry no such range, so this scale stands for both columns.

- A median absolute error (MdAPE) that moves by more than that span is called better or worse.
- A smaller move is within noise.
- This rule is applied post hoc and was not registered.

## 2. Round-trip port floor with miss merging

The preregistration's core item: since `e51f8ef` the `l2_merge_by_sharing` error rose on GB10 from 4.6% to 8.8% (old profile). Here the same IR is run on three cores and both profiles, all 51 stagger-0 points:

| Core | Profile | MdAPE | Signed median | MAPE | Signed median by CTAs: 16 / 23 / 48 / 96 |
|---|---|---|---|---|---|
| `9c12720` (before the floor) | 0.22.0 | 4.6% | +3.3% | 9.7% | +1.3 / -0.7 / +4.6 / +4.1% |
| `e51f8ef` (the floor) | 0.22.0 | 8.8% | +7.7% | 14.3% | +7.7 / +5.8 / +7.7 / +8.5% |
| `70de487` (main) | 0.22.0 | 7.8% | +7.6% | 13.8% | +7.7 / +5.8 / +7.7 / +5.5% |
| `9c12720` | **0.23.0** | 3.8% | +3.7% | 3.6% | +2.4 / +3.0 / +4.0 / +4.0% |
| `e51f8ef` | **0.23.0** | 5.7% | +5.7% | 10.0% | +9.6 / +7.4 / +5.1 / +4.3% |
| `70de487` | **0.23.0** | 4.9% | +4.9% | 8.8% | +9.6 / +7.4 / +5.1 / +4.1% |

Facts for the decision on the item; no fix is proposed.

- **The coupling persists on the qualified profile, smaller in the median.** Main's MdAPE is 4.9% against 3.8% without the floor: the median gap fell from 3.2 points (old profile, main) to 1.1.
- **The MAPE gap remains large.** 8.8% against 3.6%.
- **It sits at sparse CTA counts.** At 16 CTAs (a third of an SM count) the signed median is +9.6% with the floor against +2.4% without. At 23 it is +7.4% against +3.0%. At 48 and 96 CTAs the cores agree within 1.1 points.
- **Worst point.** Main's worst point is +35.0% (16 CTAs, sharing 16, 16 KiB).
- **No other column.** The RTX 4070 has no qualified profile, so this item has no second column. The preregistration's draft recommendation ("keep the coupling as an explicit known limit if it persists but no registered alternative wins on a qualified profile") can now be read against these numbers on GB10 alone.

## 3. Mechanisms marked provisional in the preregistration

- **Cross-wave L2 reuse, form c.**
  - Not re-checked: its microbenchmarks (`wave-rescan`) are not in the profile.
  - Its one profile input, `l2_effective_capacity_bytes`, is unchanged at 24 MiB with `rel_uncertainty` 0.1667. In 0.23.0 it carries `l2_near_capacity_unstable: true`.
  - Its standing is still set by the sealed holdout.
- **The rescan curve** (`l2_rescan_hit_rate_by_working_set`) is read by the L2 model only for warm-start hits over a kernel's whole read footprint (`eval_rescan_hit`), not by form c. In 0.23.0 the curve falls earlier and has a longer tail:
  - 21 MiB: 1.00 → 0.88;
  - 24 MiB: 1.00 → 0.79;
  - 25 MiB: 0.96 → 0.72;
  - 27 MiB: 0.03 → 0.36;
  - 30 MiB: 0.01 → 0.18.
  
  Warm kernels with footprints of 21 to 30 MiB see this; none of the re-checked sets does.
- **H7 F-dep.**
  - It is not in the core, and its registered test is the RTX 4070 `attention_compute` sweep, still pending.
  - New here: GB10's 0.23.0 profile has `mma_softmax_chain` for the first time. The current chain form (F-max) gives a signed median of -15.9% (72 points, predicted fast, worst -50.6%).
  - That is the direction F-dep would move, but F-dep is not implemented, so no counterfactual is run. This is not evidence for its registration.
- **Spill L1 transition and spill reload latency.** These are carried over and not re-checked (section 1). The carveout probe's finding stands as a known limit ([design.md 9.2](../../design.md#92-v02-residuals-and-exclusions)).
- **Measured non-MMA issue rate.** It is now a collected value in 0.23.0 (section 4). No re-checked mechanism is sensitive to it.

## 4. Large field differences and their effect

From the two formal profile files:

| Field | 0.22.0 | 0.23.0 | Change |
|---|---|---|---|
| `compute.non_mma_issue_rate_per_sm_gips` | 10.04 | 8.573 | -14.6% |
| `memory.l2_latency_loaded_ns` | 591.8 | 672.1 | +13.6% |
| `memory.dram_bw_read_gbps` | 263.6 | 242.2 | -8.1% |
| `memory.l2_rescan_hit_rate_by_working_set` | | | pointwise, section 3 (largest moves -0.24 at 25 MiB, +0.33 at 27 MiB) |

Other scalar changes over 2%: `pipeline.min_async_roundtrip_ns` -4.4%, `memory.l2_bw_read_gbps` -2.7%, `async_pipeline.cp_async_bw_per_sm_gbps` -2.1%.

**Effect on the re-checked mechanisms: none.** Each of the four fields was set back to its 0.22.0 value in the 0.23.0 profile, one at a time, and the re-check was rerun. No mechanism's MdAPE or signed median moved by 0.05 points or more. The likely reasons, not checked one by one:

- The closed-loop kernels take their compute as issue counts scaled by the same issue rate, and in the other kernels the issue pipe does not bind.
- The core reads the DRAM and L2 curves of these kernels rather than the scalars.
- The warm points' footprints are far below the rescan curve's change.

These differences can act on kernels outside the microbenchmark sets:

- the issue rate on non-MMA-heavy loops;
- the scalars where a curve is absent;
- the rescan curve on warm footprints near capacity.

Their effect there is not measured by this re-check.
