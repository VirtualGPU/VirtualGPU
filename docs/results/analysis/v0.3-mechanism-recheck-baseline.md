# Mechanism re-check on a profile's own microbenchmarks: baseline on the current profiles

`scripts/recheck_mechanisms.py` re-runs every mechanism of [design.md 6.4](../../design.md#64-mechanisms-in-the-core) that has a microbenchmark basis in the GPU profile, so that a new profile (the 0.23.0 long-launch GB10 profile first) can be compared with the old one mechanism by mechanism. It only reads the core: no mechanism, parameter or profile changes. This baseline was regenerated from the per-SM spill core at `01190e9` on `profiles/gb10.json` (`0.22.0-posthoc`) and `profiles/rtx4070.json` (`0.21.0-posthoc`). It was regenerated again at `fd1a342`, where the profile schema gained the optional spill point fields `allocation_span` and `l1_boundary_two_state`; that changes the compiled-source SHA, and no number in the baseline changed. It was refreshed again at `dec52c3`, where the core added the `cube_vector_split` single-MTE2 path for Ascend 910B3 and lifted its unvalidated gate; that changes the compiled-source SHA, and no number in the baseline changed. Every microbenchmark in these two profiles is a short launch (most points under 1 ms, see [long-launch-capture.md](../../components/long-launch-capture.md)), so their columns serve only for comparison with a long-launch profile, not as evidence for any mechanism.

    python scripts/recheck_mechanisms.py --profile gb10=profiles/gb10.json \
        --profile rtx4070=profiles/rtx4070.json \
        --out docs/results/analysis/v0.3-mechanism-recheck-baseline.json

## Method

- Each point of a mechanism's basis in the profile is written as the synthetic KernelIR of the kernel that ran (`microbench/src/m2_kernels.cuh`): grid, warps, the stage's global load (bytes, width, `cp.async` or synchronous, prefetch distance from the tokens), shared memory reads (`ldmatrix`) and writes (register staging), MMAs per CTA, ALU, SFU and shuffle counts, and for spills the frame and reload bytes.
- DRAM points stream: every CTA reads new bytes each step (a grid-wide stride), predicted with a cold L2; L2 points re-read the same stage, predicted warm. A check confirms that the first sends all load bytes to DRAM and the second hits L2 with all of them (`python/tests/test_recheck_mechanisms.py`).
- The model's per-step time is the difference of two launches, 256 and 512 steps, over 256, so launch and CTA dispatch costs drop out, as they do from the measured per-step values.
- Per mechanism and profile: points, median absolute error, MAPE, signed median error (predicted over measured minus one) and the worst point. All rows are in the JSON.

`--check` requires a clean extension built at the checkout's HEAD. It
also checks the baseline SHA-256 over the committed build paths
(`crates`, `schemas`, `Cargo.toml`, `Cargo.lock`). Documentation commits
leave that source SHA valid. The JSON also records the exact build
commit used to generate the numbers.

## Against the numbers in design.md 6.4

These were computed when each mechanism was added, on the profiles of the time, with scripts that were not kept; this tool reproduces them where it builds the same kernel.

- `sync_stage_loop` (port floor): MAPE 7.1% GB10 and 4.4% RTX 4070, the values in design.md.
- `serial_stage_fill`: 9.3% and 11.8% against 8.6% and 9.2%.
- Closed loop: median 2.8% / 2.2% (DRAM) and 5.2% / 4.9% (L2) on 252 of the 360 points per level, against 2.6% and 6.8% on all 720; the spin compute points at more than one CTA per SM cannot be written (below). `dram_closed_loop_mma`: median 2.6% / 1.3% against 1.0% to 1.9%.
- `lsu`: held-out MAPE 11.4% GB10 and 14.6% RTX 4070 (35 points each, the calibration point left out) against 13.1% and 18.0%.
- Miss merging, stagger 0: median 7.8% GB10 (51 points) and 11.3% RTX 4070 (42 points), over-predicted (+7.6%, +11.3%), against 5.0% (RTX 4070, 42 points). The 5.0% is from `c976960`, which added the merged split, and the same IR reproduces it on that core (median 4.8%, signed +3.4%, on the current RTX 4070 profile; the profile at `e46b16e` gives the same). Core by core between `c976960` and `e46b16e`, where design.md first quoted it, the error stays at 4.8% through `9c12720` and becomes 12.2% at `e51f8ef`, the round-trip port floor (GB10: 4.6% to 8.8%). The floor adds the stage's bytes over the one-SM L2 ceiling to the round trip, and these points are latency-bound reads at fewer CTAs than SMs: on the RTX 4070 the signed median is +18.0% at 16 CTAs, +13.8% at 23, +9.8% at 46 and +3.4% at 92. design.md 6.4 still quotes the pre-floor number; the port floor was judged on `serial_stage_fill` and `sync_stage_loop`, not on this basis.
- Dependent chain (RTX 4070 only; GB10 has no `mma_softmax_chain`): signed median -14.9%, -17.7% and -4.3% at 1, 2 and 3 CTAs per SM against -0.7%, -7.9% and +3.8%. design.md used the measured solo times; KernelIR carries instruction counts, here from the CUDA source, so this row also tests those counts.
- Spills, the four `l1_boundary` batch points: `cd5f35f` charges the first-wave peak instead of the hardware occupancy limit. The one-CTA-per-SM benchmark thus pays for one frame group. The signed median error falls from +209.6% to +67.6% on GB10 and from +70.7% to +38.0% on RTX 4070. The other 2,799 predicted points are bit-identical because their IR has no spill charge. Scaling the local bandwidth estimates leaves these predictions unchanged. The modeled 8 KiB carveout selects the 16 KiB miss curve, which assigns nearly all reloads to L2 at a 128 KiB footprint. The per-SM phase-entry charge reproduces all 2,807 rows bit for bit because the spill fixture has one resident CTA per SM. See the [first-wave recheck](v0.3-spill-first-wave-posthoc.md) and [per-SM follow-up](v0.3-spill-per-sm-posthoc.md).

## Not expressed

The same for every profile, so a change between columns comes from the profile:

- `closed_loop`: `compute_ns` is a `clock64` spin, written as issue work at the CTA's alone rate; with more than one CTA per SM the model would share that issue work and the spin does not, so those points (`compute_ns` over 0 and more CTAs than SMs) are left out.
- Miss merging: `stagger_stages` 16 delays the followers once at the start; KernelIR has no per-CTA start offset, so only stagger 0 is checked, the basis in design.md.
- Dependent chain: per warp per step 2 x `mma_per_half` MMAs, `softmax_ops` / 2 `ex2`, 4 shuffles and `softmax_ops` + 15 other instructions, from the CUDA source, not SASS.
- `sfu` and `shfl`: their rates are the profile's own curves, checked by leave-one-out interpolation, not by a core run; not re-run.
- Cross-wave reuse: its microbenchmarks are not in the profile.
- Loop and address instructions are not counted in any kernel.

## Reading a new profile's column

A long-launch profile moves the measured side of each mechanism by the shifts in [long-launch-capture.md](../../components/long-launch-capture.md), section 3 (the last column above). With the model inputs unchanged, a measured shift of s moves the signed error by about -s; the new profile also changes the curves the model reads (bandwidth, latency, MMA rates), so a column-to-column change beyond the listed shift is a change in what the model is given, to be traced to the fields that moved, before it is read as evidence about a mechanism.
