# Per-SM spill footprint follow-up registration

Registered on top of `d5a848e` before adapting the per-SM implementation
to the first-wave correction. The original plan (`e7fed3a`) and its
implementation (`5d7262d`) are preserved at `bc09edb` on
`archive/s5-v03-spill-residency`. Their replay is legacy post-hoc evidence. This follow-up leaves the
frozen v0.2 conclusions in force.

## Charge and scope

The current model applies the maximum first-wave CTA count at every SM.
At each spill-bearing phase entry, count resident CTAs on that SM after
all completions and refills at that timestamp. Use that count times
warps per CTA, warp size and frame size to size the footprint. Divide
the aggregate traffic by the same count and use its miss fraction for
the reload lookup. Phase demands stay fixed until the next phase.
The largest realized initial count still seeds the existing persistent
L2 spill pressure. Smaller charges use that pressure and the initial
L2 working-set convention.

## Acceptance

- The sparse, uneven, full-wave and tail fixtures must use the expected
  CTA counts and preserve per-CTA traffic. The full-residency charge
  matches the first-wave model.
- With the same two legacy profiles and the current first-wave recheck
  as the baseline, all 2,807 synthetic point predictions must remain
  bit-identical. Its spill benchmark uses one CTA per SM with uniform
  residency. The earlier reductions in error versus the hardware
  occupancy charge remain provisional.
- For the archived v0.2 IR replay, use the same profile bytes, warm and
  cold, draw 0 plus 32 perturbations and seed 17. Report all timing
  changes and statuses. Every spill-free prediction must remain
  bit-identical. The full-wave-plus-one-CTA witness compares two models
  and has no corresponding hardware measurement.
- Issue #21's freeze gate requires an unmodified invocation of
  `scripts/spill_decision.py freeze` with the frozen profile arguments.
  Its raw output must match
  [the issue #15 frozen decision JSON](v0.3-spill-decision-frozen.json)
  byte for byte. Archive both SHA-256 values and the actual comparison.
  A provenance change is still a byte difference under this gate.
  A separate comparison may isolate prediction data for diagnosis.
  Any different acceptance rule requires an explicit recorded decision.

## Issue #21 clarification

The accepted comparison requires the original clean `cd5f35f` output to
reproduce the registered JSON byte for byte. A clean candidate output
may differ only in the value of `core.commit`, which must identify the
candidate build. Every other byte, including `dirty`, `result_class`,
the script and profile digests, and the predictions, must match.
The [issue #21 clarification](https://github.com/VirtualGPU/VirtualGPU/issues/21)
authorizes this interpretation of the original gate. The scorer, inputs
and frozen file retain their registered bytes.
